# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is **pnpm** (`packageManager: pnpm@10.9.0`). All tasks run through Nx.

```sh
# Whole workspace
pnpm build          # nx run-many --target=build --all
pnpm test           # nx run-many --target=test --all
pnpm lint           # nx run-many --target=lint --all
pnpm type-check     # nx run-many --target=type-check --all (tsc --noEmit per project, cached)

# Per-app (bff, invoice, product, user-access) — same pattern for each
pnpm invoice:dev     # nx serve invoice
pnpm invoice:build   # nx build invoice
pnpm invoice:test    # nx test invoice
pnpm invoice:lint    # nx lint invoice

# Single test file / single test name
nx test invoice -- invoice.service.spec.ts
nx test invoice -- -t "creates an invoice"

# e2e (invoice-e2e, bff-e2e) — requires the target service's deps running
docker compose -f docker-compose.dev.yml up -d redis mongodb user-access
nx e2e invoice-e2e
```

Test/build/lint targets on every app and most libs are **inferred by Nx** from the presence of `jest.config.cts` / eslint config / `webpack.config.js` (see the `plugins` block in `nx.json`), not hand-written per project. A lib with no `jest.config.cts` has no `test` target at all — copy an existing lib's (e.g. `libs/transports`) `jest.config.cts` + `tsconfig.spec.json` + the `tsconfig.spec.json` reference in `tsconfig.json` when adding tests to a lib that doesn't have them yet. `type-check` is the one target that is **not** inferred: each `project.json` declares it explicitly (`tsc -p {projectRoot}/tsconfig.app.json|tsconfig.lib.json --noEmit`; e2e projects use `tsconfig.spec.json`, since their `tsconfig.json` is `files: []` and would check nothing), with caching/inputs from `targetDefaults` in `nx.json` — add one when creating a project. A lib whose spec files exist but has no `jest.config.cts` silently never runs them — `libs/circuit-breaker`'s spec sat in that state, didn't compile, and was hiding a real bug once it finally ran. Likewise **every lib needs a `project.json`**: without one Nx leaves it out of the project graph entirely, so an app's build cache doesn't invalidate when that lib changes and `nx build` replays a stale bundle (hit with `libs/cache`; `auth`/`cache`/`rate-limit`/`circuit-breaker`/`audit-log` were all missing one).

### Testing layers

See `docs/testing-microservices-strategy.md` (an eight-part series) and `docs/testing-implementation-plan.md`. Each layer has its own convention:

- **Unit** — `*.spec.ts`, `pnpm test`. Test guards with Nest's real `Reflector`, real decorated controller classes and `ExecutionContextHost`, not stubbed metadata lookups; test JWT/webhook code with real crypto (`jwt.strategy.spec.ts` signs RS256 tokens, `stripe-payment.provider.spec.ts` uses stripe-node's `generateTestHeaderString`). Any lib whose spec compiles an ESM dependency that default-imports CommonJS (e.g. `@nestjs/passport` → `passport`) needs `"esModuleInterop": true` in its `tsconfig.spec.json`.
- **Transport** — `*.transport.spec.ts`, run by `pnpm test` (sockets, no Docker): real Nest microservices with the same global guards/interceptors as `main.ts`, called with real `ClientProxy`/`ClientGrpcProxy`. Build configs with the production factories and adapt them with `forTest(config, port)` / `freePort()` from `@libs/transports/transport-test-harness` (spec-only, subpath import — it repoints `.proto` paths at `libs/transports/src/proto`, since `grpc.config.ts` resolves them next to the bundled `main.js`). In `afterAll`, close servers before clients: a client whose setup failed may never settle `close()`, and a server left listening hangs Jest instead of failing it.
- **Integration** — `*.int-spec.ts` with Testcontainers (Redis, Postgres, MongoDB, `adobe/s3mock`) or a real Chromium; `pnpm integration` or `nx run <project>:integration`. Never part of `nx test`: each such project has a `jest.integration.config.cts` and an explicit `integration` target (`cache: false`, `runInBand`), `tsconfig.spec.json` includes `src/**/*.int-spec.ts`, and the app/lib build tsconfig excludes it. Add all four when giving a new project integration tests. `user-access`, `product` and `payment` each assert their migrations produce zero schema drift against the entities (`createSchemaBuilder().log()` must be empty) — copy that check into any new TypeORM app. A drift check can't see data loss (DROP + ADD COLUMN ends at the same schema), so `payment`'s suite also runs each migration's `up()` with rows written between them and asserts a `paid` payment survives the status-widening migration; do the same for any migration that rewrites an existing column. The Chromium suite fails, never skips, when no browser is found (`PUPPETEER_EXECUTABLE_PATH`). On macOS, `Timed out after 30000ms while waiting for container ports to be bound to the host` is Docker Desktop being slow to publish port bindings while many containers run (the 30s is hard-coded inside Testcontainers, seen twice with the ~18-container dev stack up) — the container itself is healthy; re-run, or stop the dev stack first. Not seen on native-Linux Docker (CI).
- **Contract** — golden fixtures in `libs/transports/src/contracts/kafka/` are the exact wire values for `invoice.events`, asserted by the TS producer (`invoice-events-producer.contract.spec.ts`) _and_ the Go consumer (`services/mail/internal/events/contract_test.go`). Changing the event shape means changing a fixture. Go's `encoding/json` matches keys case-insensitively, so a casing-only tag change is not a contract break. `bff`'s `authorizer-permission.resolver.transport.spec.ts` is the consumer-side gRPC contract against a stub served from the real `authorizer.proto`.
- **Go** — `pnpm mail:test`; CI runs `gofmt -l`, `go vet`, `go test -race` in `services/mail`. Go integration tests (`//go:build integration`, `pnpm mail:integration`, also a CI step) use testcontainers-go against real Kafka (`apache/kafka:4.3.1` via a generic container with a fixed host port — the testcontainers Kafka module only accepts `confluentinc/confluent-local`), Redis and s3mock; the consumer test proves an offset interrupted mid-retry is redelivered to the next group member. **Keep `go.mod` at the Go version `services/mail/Dockerfile` builds with (`golang:1.25-alpine`, `GOTOOLCHAIN=local`)**: `go get …@latest` silently raised the directive to 1.26 via `go-redis` v9.23 (pinned v9.22.0) — check `head -3 go.mod` after any `go get`. CI's `setup-go` reads the version from `go.mod`, so it would _not_ catch the mismatch; only the image build does.
- **E2E (invoice)** — `apps/invoice-e2e`, `nx e2e invoice-e2e`, needs `docker compose ... up -d redis mongodb user-access` (issuing reads the organization's invoice prefix from user-access; setup fails fast if its TCP port isn't open), with the dev invoice container stopped (it holds 3302). Requests send `X-Organization-Id: <default organization>` (`support/test-setup.ts`). Its `global-setup.ts` spawns the _built_ app (`dependsOn: invoice:build`) as a child process it owns and `global-teardown.ts` kills exactly that process — it does **not** depend on `invoice:serve`: when the run ended, Nx's node executor was left orphaned and kept serving on 3302 indefinitely, so the next run's readiness check was answered by a stale process. Setup refuses to start if 3302 is already in use. It reads `INVOICE_HTTP_PORT`, never the generic `PORT` (Nx injects the root `.env`, which sets `PORT=3300`, bff's port), and spawns the app with `NODE_ENV=development` (Jest sets `test`, which would load a nonexistent `.env.test`). A host-run app also needs every var compose normally supplies — a local `.env.dev` that has fallen behind `.env.dev.example` (e.g. no `REDIS_PASSWORD`) fails with `NOAUTH` against the dev Redis.
- **E2E** — `apps/bff-e2e`, `pnpm e2e`, against the running dev stack (no `dependsOn: bff:serve`, no `killPort` teardown — the scaffold's version would kill Docker's port forwarder). The dev users need memberships first: `nx run user-access:seed-dev-memberships`. `bearer()` sends `X-Organization-Id` (the default organization) on every request — the dev users may belong to more than one organization, and a multi-membership caller without the header gets a 400. `global-setup.ts` waits for `/api/health/ready` and logs in **once** through `bff`'s `/auth/login`, sharing tokens via `process.env` — `/auth/login` is limited to 5 per IP, so per-file logins 429 the suite. Rate-limit buckets are keyed by IP + method + route pattern and Jest orders files by past duration, so a spec that drains a bucket must use a route no other spec calls (`rate-limit.e2e.spec.ts` uses `GET /users/:id`).
- **Load** — `pnpm load:bff` runs `load-tests/k6/*.js` in `grafana/k6:2.3.0` on the `einvoice-dev_edge` network. All virtual users share one IP behind a per-IP limiter, so the script asserts graceful shedding (429 + `Retry-After`, never 5xx) and latency of _admitted_ requests, with `setResponseCallback(expectedStatuses(200, 201, 429))`.
- **CI** — `.github/workflows/test.yml`: `unit` (lint, type-check, test), `integration` (Docker + Chrome are preinstalled on GitHub's Ubuntu runners), `go`. E2E and load stay manual.

### Docker Compose

- **MongoDB is a single-node replica set** in both compose files (invoice's transactional outbox needs multi-document transactions, which standalone MongoDB doesn't have). `--replSet rs0` with auth needs a keyFile; with one member any key works, so the entrypoint generates one per start. The healthcheck runs `rs.initiate()` on first boot (idempotent) and is healthy only once the node is a writable primary. An existing standalone volume converts in place (verified with data). The member advertises `mongodb:27017`, which only resolves inside the compose network, so **host-run apps (e2e, `nx serve` on the host) need `MONGODB_DIRECT_CONNECTION=true`** (`.env.dev.example`; `apps/invoice-e2e/src/support/global-setup.ts` sets it explicitly) — without it the driver fails with `ENOTFOUND mongodb`. Testcontainers' `MongoDBContainer` is already a replica set. Third-party images are pinned (`apache/kafka:4.3.1`, `adobe/s3mock:5.2.3` — both were `latest`, including in the media integration test, so CI was unpinned too); pin by matching the local image digest to a Hub tag, not by guessing.
- Dev: `cp .env.dev.example .env.dev && docker compose -f docker-compose.dev.yml up --build` — mounts the full workspace into containers, runs `pnpm nx serve <app>`, exposes Postgres/Mongo/Redis/pgAdmin to the host.
- Observability: add `-f docker-compose.observability.yml` to either base file (`docker compose -f docker-compose.dev.yml -f docker-compose.observability.yml up -d`) — see the Observability section below. Grafana on `127.0.0.1:3000`, Prometheus on `127.0.0.1:9095` (not 9090: dev's `s3mock` publishes that).
- After a dependency change, dev containers share one `node_modules` named volume populated at image build time — run `docker exec -e CI=true einvoice-dev-bff-1 sh -c 'cd /app && pnpm install --frozen-lockfile'` once (it updates the shared volume for every service; `CI=true` because pnpm otherwise blocks on an interactive "reinstall from scratch?" prompt), then recreate the app containers.
- Prod: `cp .env.prod.example .env.prod && docker compose -f docker-compose.prod.yml up -d --build` — multi-stage build via the root `Dockerfile` (`ARG APP_NAME` selects which app to build/run), internal-only `backend` network, no host port publishing for internal services. **Every app's prod image builds and boots** (verified by running each against the dev stack: health live/ready green, bff end to end through login → JWT → gRPC). Four defects kept the prod path from producing anything runnable until then: `postgres` had no `image:` (compose config failed); the Dockerfile ran `nx run <app>:prune-lockfile`, which needs a per-app `package.json` no app has — the build already emits a pruned `package.json` + `pnpm-lock.yaml` (`generatePackageJson`), so the step and the `prune-lockfile`/`copy-workspace-modules`/`prune` targets were removed; the runtime stage copied only `main.js`, dropping the gRPC `.proto` files and pdf-generator's EJS templates that load from next to it — it copies all of `dist/apps/<app>/` now; and the bundle did `require("tslib")` (`importHelpers: true`), which `generatePackageJson` never lists (the compiler emits that import, source never contains it), so every image crashed with `Cannot find module 'tslib'` — `tsconfig.base.json` now has `importHelpers: false` (helpers are inlined). **Verify a prod image by booting it**, not by a green build: the last two only show at runtime.
- **Prod Keycloak needs one manual one-time setup step** the compose file deliberately doesn't automate: `docker-compose.prod.yml`'s `keycloak` service does _not_ mount or auto-import `infra/keycloak/realm-export/` the way dev does — that file hardcodes a client secret and two test users with a publicly-known password (both are in this repo's git history), so importing it into "production" would mean Keycloak actually stores those exact dev credentials rather than whatever real secret `.env.prod`'s `KEYCLOAK_CLIENT_SECRET`/`KEYCLOAK_ADMIN_CLIENT_SECRET` configure — `bff`/`user-access` would then hold a secret Keycloak never agreed to. The `einvoice` realm, both clients (`einvoice-bff`, `einvoice-admin-cli` — the latter needs `manage-users`+`view-users`+`view-realm` on `realm-management`, see the `user-access` note below), and every real user need to be created by hand (console or Admin REST API) with real secrets before `bff` or `user-access` can actually boot successfully — confirmed live (without going through the still-broken prod Docker build) that both apps' eager `CONFIGURATION.validate()` genuinely throws without these vars set, and passes once they are.

## Architecture

Nx monorepo. Deployable apps live in `apps/`, all sharing infrastructure libs under `libs/*` via TypeScript path aliases (`@libs/<name>`, mapped in `tsconfig.base.json`) — except `services/mail`, a Go service that can't join that workspace at all (no `package.json`, nothing for Nx's project graph to attach to) and deliberately sits outside `apps/` as a result; see the Kafka section below.

- **`apps/bff`** — public-facing API gateway. Owns Swagger, rate limiting, response envelopes, circuit breakers. Talks to `apps/invoice` only over TCP (via `@nestjs/microservices` `ClientProxy`), never touches Mongo/Postgres directly.
- **`apps/invoice`** — the actual invoice microservice. Exposes the same CRUD both as local HTTP (`invoice-http.controller.ts`, for direct/internal use) and as TCP `@MessagePattern`s (`invoice-rpc.controller.ts`, for the BFF). Owns the Mongo connection and all invoice persistence. Listing defaults to offset pagination (`page`, with `total`/`totalPages`); cursor pagination is opt-in — `pagination=cursor` returns the first page plus a `cursor`, then pass `cursor` (see `docs/PAGINATION-ARCHITECTURE.md`). Mixing modes (`pagination=cursor`+`page`, `pagination=offset`+`cursor`, `cursor`+`page`) is a 422. **Invoice lifecycle:** status is never written through create/update — `status` isn't in either DTO, and `InvoiceRepository.toContentPayload` allow-lists content fields because RPC payloads (`RpcEnvelope<Dto> | Dto` reflects as `Object`) skip the ValidationPipe entirely, so a DTO field removal alone is not enforcement on the TCP path. Every change goes through `InvoiceRepository.transitionStatus` (one conditional `findOneAndUpdate` that also `$inc`s `version`, so an in-flight draft edit fails its optimistic-concurrency save once the invoice is issued underneath it) against `INVOICE_TRANSITIONS` in `@libs/shared/types` (draft→issued→paid|overdue|cancelled, overdue→paid|cancelled; paid/cancelled terminal). Requesting the status an invoice already has is a no-op success (Stripe redeliveries, client retries); any other illegal change is a 409 naming the current status. Only drafts can be PATCHed or DELETEd — enforced in the same atomic filter, with a re-read only to pick 404 vs stale-version 409 vs wrong-status 409. Endpoints: `POST /invoices/:id/issue|cancel|send`. `POST /:id/pdf` only renders; `send` issues a draft, re-renders (so the PDF shows the issued state) and emits `invoice.sent` — it's the only thing that emails the client. Audit entries get `actor` centrally in `AuditLogService` (context `userId`, else `service:<sourceService>`), status changes record `diff: { status: { from, to } }`. Phase 1 of a roadmap — see `docs/invoice-lifecycle-implementation-plan.md`. **Events go through a transactional outbox (Phase 2):** `InvoiceRepository.create/transitionStatus/setPdfMetadata` run in a Mongo transaction and accept an `inTransaction(invoice, session)` hook; `InvoiceEventsProducerService.enqueue*` writes the event to the `outbox` collection in that same session, so an event exists iff its state change committed (a hook failure rolls both back). `OutboxRelay` (`modules/outbox/`) publishes committed rows oldest-first with an awaited, acked kafkajs send (`idempotent: true`), under a Redis leader lease (`svc:outbox:relay:leader`), stopping a batch at the first failure so an aggregate's events never reorder; delivery is at-least-once, consumers dedupe on `eventId` (the outbox row id, stamped into every event). Metrics: `outbox.publish{outcome}` and `outbox.oldest_unpublished_age` (relay lag). PDFs are **private**: the invoice stores `pdfKey` (S3 key), never a URL — `GET /invoices/:id/pdf` (`invoice:read`) returns a fresh 5-minute presigned link (bff never caches it); `pdfUrl` from before was converted by `nx run invoice:backfill-pdf-keys`. `send`/`generatePdf` through invoice's _local HTTP_ API can't work: the downstream pdf-generator/media RPCs require caller identity, which only bff's TCP calls carry (known gap — the local HTTP API is unauthenticated). See `docs/phase-2-private-documents-reliable-events-plan.md`.
- **`apps/product`** — product catalog microservice, following the same dual-transport pattern as `invoice`: local HTTP (`product-http.controller.ts`) and TCP `@MessagePattern`s (`product-rpc.controller.ts`) over the same `ProductService`. Unlike `invoice` (MongoDB), it owns a **Postgres** connection via TypeORM (`src/database/postgres.module.ts`, `src/database/entities/product.entity.ts`) — the first real consumer of the `postgres` container the compose files already provisioned. Currently exposes create + list only. Schema is managed entirely by migrations (`src/database/migrations/`, run via `pnpm product:migration:run`) — `synchronize` is always off, in dev too; see `apps/product/README.md` for the full migration workflow, including why `src/database/data-source.ts` (the CLI's entry point) deliberately avoids `@libs/*` aliases and the app's `CONFIGURATION` singleton. Owns its own `svc`-prefixed Redis list cache too (`CacheModule.forRoot('svc')` in `product.module.ts`, mirroring `invoice.service.ts`'s exact version+hash-keyed list caching, invalidated by bumping a Redis counter on write) — this needed `CACHE_CONFIG: RedisCacheConfiguration` added to `apps/product/src/configuration/index.ts` and Redis env vars added to both compose files, neither of which `product` had before (`CacheModule`'s factory reads `CACHE_CONFIG` off the app's `Configuration` singleton — a service can import `CacheModule` correctly and still crash at boot with "Cannot read properties of undefined" if its own `Configuration` class never declared that field).

- **`apps/user-access`** — identity/access data microservice, same dual-transport shape again (`role-http.controller.ts`/`role-rpc.controller.ts`, `user-http.controller.ts`/`user-rpc.controller.ts`). Also owns Postgres via TypeORM, sharing the same database/instance as `product` (separate tables, separate migrations directory, same connection). Two modules: `RoleModule` (read-only — roles are managed by seeding, not an API; `pnpm nx run user-access:seed-roles` upserts `src/database/seeds/roles.seed.json` by `name`, safe to re-run) and `UserModule` (full CRUD: create/list/get/update/deactivate, deactivate being a soft `isActive: false` rather than a delete). `UserEntity` has **no password field** — credential storage is deliberately out of scope until an identity provider is introduced (see `docs/introducing-keycloak.md`). A `ManyToOne(..., { eager: true })` relation from `UserEntity` to `RoleEntity` bit us during development: eager relations only auto-join on `repository.find()`/`findOne()`, not on `createQueryBuilder()` (needs an explicit `.leftJoinAndSelect()`) or on the entity `save()` returns (needs a re-fetch) — see `UserRepository` for both fixes, and note `update()`/`deactivate()` use a direct `repository.update(id, partial)` rather than load+merge+save specifically because saving an entity with an already-loaded (and by-then-stale) relation object silently overwrites the join column you just tried to change. Also runs a _third_ transport, gRPC (`role-grpc.controller.ts`'s `RoleQueryService`), alongside its existing HTTP and TCP — see the gRPC section below.
- **`apps/authorizer`** — new microservice with no database of its own; pure orchestration. Exposes one gRPC method, `ResolveCaller` (replaced `GetPermissionsForRoles` in Phase 3 — see the Tenancy section), that `bff` calls to resolve a caller's active organization, role and permissions from their memberships, via `user-access`'s gRPC `MembershipQueryService`/`RoleQueryService`, caching memberships and roles 60 s each. Replaced `bff`'s old in-process `UserPermissionResolver` (which called `user-access` over TCP directly) — see the gRPC section below and `docs/grpc-authorizer-implementation-plan.md`.

- **`apps/pdf-generator`** — stateless, no database (same shape as `authorizer`). One TCP method: renders an invoice to HTML via EJS (`src/templates/invoice.ejs`) then to PDF via Puppeteer against a system Chromium (`puppeteer-core`, not Puppeteer's own bundled download, which is glibc-only and unreliable on this repo's musl-libc Alpine images). The one browser instance is launched once at startup and reused per request (`PdfRendererService`'s `onModuleInit`), the same "expensive resource, cheap reuse" shape as this repo's DB connections. Chromium is installed into the shared dev image conditionally on `APP_NAME` (a build arg every `docker-compose.dev.yml` service now passes, not just this one) and into the prod image only when `APP_NAME=pdf-generator` — confirmed live that _not_ scoping this inflated every other service's dev image from ~1.1GB to 2.2GB for a dependency they never use. A real bug caught live, not hypothetical: `invoice.ejs` originally referenced optional fields (`dueDate`, `notes`) as bare identifiers, which throws under EJS's `with(locals)` the moment the field is actually absent (not just falsy) — a TCP payload with an unset optional key arrives with that key missing entirely, since `JSON.stringify` drops `undefined`-valued keys. Fixed via EJS's `locals.x` accessor, which never throws for an absent key.
- **`apps/media`** — stateless, no database. Two TCP methods — `UPLOAD` (`invoice:write`; stores under an unguessable `orgs/<organizationId>/invoices/<uuid>/<fileName>` key and returns **only the key**; pre-tenancy keys are `invoices/<uuid>/…`, and only the default organization may sign them) and `GET_DOWNLOAD_URL` (`invoice:read`; `HeadObject` first so a missing object is a clean 404, then a presigned `GetObject`, 60 s–1 h, default 5 min, with an RFC 6266 `Content-Disposition`). The bucket is private; nothing ever links to an object directly. Presigning uses a second S3 client built with `S3_PUBLIC_ENDPOINT` (dev: s3mock's host port) — the signature covers the host, so a URL signed for the in-network `s3mock:9090` can't just be rewritten for a browser; unset on AWS. s3mock does not verify signatures (verified), so expiry/tampering can only be tested against real S3. Both go through a `StorageProvider` interface (`src/app/modules/media/storage-provider.interface.ts`) whose only implementation is `S3StorageProvider` — same "one small interface, one swappable class" DI shape as `PermissionResolver`. `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` are optional on purpose: left unset (the production default), the AWS SDK falls back to its own default credential chain (an ECS task role / EC2 instance profile) instead of a static key pair in an env var. Dev backs this with `adobe/s3mock`, the third S3-compatible image tried in a row — MinIO and then LocalStack both turned out to gate their easy-to-pull images behind a paid registry login/license as of their 2025/2026 changes, confirmed live (anonymous pulls 401, or the container refuses to start without a license token) rather than assumed from memory.
- **`apps/payment`** — Postgres-backed (TypeORM), same dual-transport shape as `product`/`user-access`. Stripe is fully encapsulated behind a `PaymentProvider` interface (`createCheckoutSession`/`parseWebhookEvent`) — same DI shape as `StorageProvider`. **The Stripe webhook is received by `bff`, not by `payment` directly** — `bff` stays the only public-facing ingress in this repo (the same role it already has for Keycloak, rate limiting, Swagger), capturing the raw request body via a `verify` callback on its existing `json()` body-parser middleware and relaying only the raw bytes + `stripe-signature` header to `payment` over TCP; `payment` does the actual `stripe.webhooks.constructEvent` signature verification, so the webhook secret never needs to exist in `bff`'s environment. That webhook RPC handler is deliberately `@Public()` — a webhook call carries no end-user identity to check, the same service-to-service exception `user-access`'s `RoleGrpcController.findAllRoles` already established — and narrow (it only ever flips an invoice's status to `paid`, calling `invoice` over its own equally narrow, equally `@Public()` `MARK_PAID` pattern), rather than widening the general-purpose `UPDATE` pattern that real user edits still go through permission-gated. **Checkout and webhook rules:** a checkout session is only created for an `issued`/`overdue` invoice (409 otherwise). An open (`pending`) session is reused while it has >30 min left (`payments.expiresAt`, from Stripe's `expires_at`); otherwise it's expired at Stripe _first_, then marked `failed`, then replaced — self-healing if a `checkout.session.expired` webhook was lost. A partial unique index (`UQ_payments_open_session_per_invoice`, `invoiceId WHERE status = 'pending'`) makes reuse race-safe: a concurrent loser's saga compensation expires its own session and it returns the winner's URL. On the webhook, a 404/409 from `invoice`'s `MARK_PAID` (e.g. the invoice was cancelled after checkout began) is flagged `reconciliation_required` and **acknowledged** — retrying can't change a deterministic refusal — while transient failures still propagate so Stripe retries. A second successful payment for an invoice that already has a `paid` payment is flagged `reconciliation_required` (refund owed) instead of looking like a normal success, since `markPaid` is idempotent. **Consumes `invoice.cancelled`** (`InvoiceEventsController`, consumer group `payment`) and expires the invoice's open checkout session (`expireOpenSessionForInvoice` — idempotent; a Stripe failure rethrows so Kafka redelivers). **payment runs two microservice servers (TCP + Kafka), so every handler names its transport** (`@MessagePattern(…, Transport.TCP)`, `@EventPattern(…, Transport.KAFKA)`): Nest binds a pattern with no transport to _every_ server, so the Kafka server tried to subscribe to the TCP pattern strings as topics and payment failed to start — found only by running the stack live; `transport-binding.spec.ts` pins it. Prod compose was missing payment's `INVOICE_SERVICE_HOST` (the client fell back to `localhost`, i.e. its own container, so every checkout and every webhook mark-paid would have failed); fixed.

Each of `bff`/`invoice`/`product` has an `*-e2e` sibling project that hits the real running app over HTTP (not mocked) — these need the app served (`nx serve <app>`) and its DB/cache dependencies up first; they're not run as part of the default `nx test` target.

### Tenancy, invoice numbering, customers (Phase 3)

einvoice is multi-tenant: every invoice, customer, product, payment, audit entry, outbox event and PDF belongs to one organization. See `docs/phase-3-tenancy-numbering-customers-plan.md` (decisions + verification record). The short version:

- **Model (user-access, Postgres):** `organizations` (`slug`, `invoicePrefix`) and `memberships` (user × organization × role, unique per pair) replaced `users.roleId`; a person can belong to several organizations with a different role in each. Roles have a `scope`: `organization` roles are assigned through memberships; `platform-admin` (`platform:admin`) is a Keycloak realm role and grants nothing inside an organization. `POST /organizations` (platform admin) creates an organization together with its first admin (saga). Pre-tenancy data lives in the **default organization**, `DEFAULT_ORGANIZATION_ID` (`00000000-0000-4000-8000-000000000001`, `@libs/shared/types`), created by user-access's migration — migrations hard-code the literal (no `@libs` aliases there).
- **Resolution:** bff's `PermissionGuard` sends the caller and the optional `X-Organization-Id` header to authorizer's `ResolveCaller`: `resolved` (exactly one membership, or the header names one of theirs), `ambiguous` (several, no header → 400 on tenant routes), `not_member` (403, on every route), `none` (403). The header is a request, never trusted. Routes without `@RequirePermission` (`GET /me`) work while unresolved. The resolved organization goes into the correlation context and from there into every `RpcMeta` (`organizationId`) and outbox event.
- **Enforcement:** repositories scope themselves with `requireOrganizationId()` (`@libs/logging`), which **throws** without an organization — an unscoped query on tenant data must be impossible. Another organization's record is always _not found_ (404), never 403. Cache keys go through `tenantCacheKey(namespace, …)` (`@libs/cache`) → `<ns>:org:<org>:…`, list-version counters included. `RpcPermissionGuard` refuses a handler requiring a tenant (non-`platform:`) permission when the envelope has no organization. A `@Public()` service-to-service handler reached without one throws `MissingOrganizationContextError`, which `RpcExceptionInterceptor` maps to 400 and the internal HTTP apps' `MissingOrganizationContextFilter` (`@libs/filters`) maps to a 400 naming the header.
- **Where no caller supplies the organization**, it comes from data: the Stripe webhook finds the payment by session id (the one deliberately unscoped lookup) and runs mark-paid with `runInOrganization(payment.organizationId, …)`; payment's `invoice.cancelled` consumer uses the envelope's organization, falling back to the default organization for events published before tenancy (throwing would make Kafka redeliver forever). invoice reads its prefix through `ORGANIZATION.INVOICE_SETTINGS`, a `@Public()` pattern returning only `{ invoicePrefix }` for the envelope's organization — numbering must also work with no end user behind it (internal API, scheduled issuing later).
- **Internal HTTP APIs** (invoice/product/payment/user-access ports, never bff) take the organization from `X-Organization-Id` as-is (`InternalCallerContextMiddleware`), trusted by network placement like the rest of those ports.
- **Numbering:** drafts are unnumbered; `issue` assigns `{prefix}-{year}-{000001}` (UTC year of issue, gapless per organization and year) and sets `issueDate` to the moment of issue, refusing (422) a draft whose due date has already passed. The counter (`invoice_counters`, `_id: "<org>:<year>"`) is created idempotently _before_ the transaction (two first-of-year issues racing to insert it inside transactions would fail with a non-retryable duplicate key) and `$inc`'d _inside_ the issuing transaction via `transitionStatus`'s `prepare` hook, which runs only after the status check — an aborted issue gives its number back, a refused one never takes one, and concurrent issues serialize on the counter (verified with 10 in parallel). `(organizationId, invoiceNumber)` is unique as a backstop. Clients can no longer send `invoiceNumber`; `reference` (their PO number, searchable) replaced it.
- **Customers** live in the invoice service (`modules/customer/`, Mongo, `customer:read|write`): `POST /invoices` takes `customerId` **or** an inline `client` (exactly one — re-checked in the service, since RPC payloads skip validation); a customer is snapshotted onto the invoice, so editing or deleting it never changes an invoice. Email is unique among an organization's live customers. bff: `/customers` CRUD and `GET /customers/:id/invoices` (404 for a customer outside the organization, not an empty list).
- **Mongo indexes in production:** invoice runs with `autoIndex` off in production, so **nothing built Mongo indexes there** (the Phase 2 outbox indexes included). `nx run invoice:sync-indexes` (`--args=--dry-run` reports) makes every owned collection's indexes the schemas' (`syncIndexes`, which also drops undeclared ones) — run it on every deploy that changes an index. `src/database/index-sync.ts` lists the owned models; `tenancy-migration.int-spec.ts` is the Mongo drift check (`diffIndexes()` empty). These scripts run under `@swc-node/register`, which resolves `@libs/*` aliases (ts-node doesn't), so they use the real schemas instead of a copy — and swc's decorator metadata is why `AuditLog.action` now declares `type: String` explicitly (swc emits `Object` for a string-literal union; tsc emits `String`).
- **Deploying Phase 3 onto existing data:** user-access/product/payment migrations (default-organization backfill; product SKUs become unique per organization), then — with invoice stopped — `nx run invoice:backfill-tenancy` (idempotent, `--dry-run`; drops the legacy _global_ `invoiceNumber_1`/`idempotencyKey_1` first — `invoiceNumber_1` isn't sparse, so it counts a missing number as null and would reject un-numbering a second legacy draft; moves legacy drafts' client-chosen numbers into `reference`; seeds counters past existing `{prefix}-{year}-NNNNNN` numbers; assigns invoice audit entries), then `nx run invoice:sync-indexes`. Verified on the dev database (138 invoices, 214 audit entries).
- **Testing tenant code:** `itInOrganization as it` and `TEST_ORGANIZATION_ID` (a UUID — Postgres columns are typed `uuid`) from `@libs/logging/testing` run each test body inside an organization context. `AsyncLocalStorage.enterWith()` in a `beforeEach` does _not_ reach the test body under Jest; the context has to wrap the test function. Use plain `test(...)` for "refuses without an organization" cases.

### Gateway → microservice RPC pattern

The BFF never imports invoice's Nest module. Instead each gateway feature module (e.g. `apps/bff/src/app/modules/invoice/`) has its own `*-client.service.ts` extending `@libs/transports`'s `BaseTcpClient`, which wraps `ClientProxy.send()` with: an `RpcEnvelope` (correlation/trace id propagation, see `libs/transports/src/lib/rpc-envelope.ts`), a timeout, and HTTP-exception mapping (`GrpcToHttpMapper`/`ConnectionErrorDetector` translate RPC failures into the right `HttpException`, including `ServiceUnavailableException` when the invoice service is down). The BFF's own service layer then wraps that client with caching (`CACHE_MANAGER` + a Redis-backed list-version counter for cache invalidation) and an optional circuit breaker (`@libs/circuit-breaker`) that falls back to serving stale cached data when open. `TCP_PATTERNS`/`TCP_CLIENT_TOKENS`/`ServiceName` in `@libs/transports` are the single source of truth for which pattern strings and DI tokens exist per service — add new RPC endpoints there first.

### gRPC transport pattern (`bff` → `authorizer` → `user-access`)

Two hops use gRPC instead of this repo's usual TCP transport, deliberately — the point of `apps/authorizer` was trying gRPC specifically, not that TCP was failing at anything; `invoice`/`product` are unaffected and still use TCP exactly as before. See `docs/grpc-transport-in-microservices.md` through `docs/grpc-authorizer-to-user-access-communication.md` (a six-part series) for the full walkthrough, including a real bug this pattern's own live verification caught. The short version:

- `.proto` contracts live in `libs/transports/src/proto/` (`authorizer.proto`, `user-access.proto`) — the same single-source-of-truth role `TCP_PATTERNS`/`ServiceName` play for the TCP side. `createGrpcServerConfig`/`createGrpcClientConfig` (`libs/transports/src/lib/grpc.config.ts`) mirror `createTcpServerConfig`/`createTcpClientConfig`'s shape; `GrpcServiceName`/`GRPC_SERVICES`/`GRPC_CLIENT_TOKENS` are gRPC's equivalent of `ServiceName`/`TCP_CLIENT_TOKENS`.
- **`.proto` files need an explicit webpack `assets` entry in every app that touches gRPC** (`authorizer`, `bff`, `user-access`) — `join(__dirname, 'proto')` in `grpc.config.ts` resolves at runtime inside that app's own bundled `dist/apps/<app>/main.js`, not `libs/transports`' source tree, and webpack won't bundle a non-JS file into `main.js` just because TypeScript references its path as a string. Same class of bug as `ratelimit.lua`'s ENOENT (`@libs/rate-limit`) — verify with `ls dist/apps/<app>/proto/` after a real build, don't assume the config alone is enough.
- No codegen (`ts-proto` etc.) — both `.proto` contracts are small and stable enough that hand-written TypeScript interfaces matching them (`apps/authorizer/.../grpc-contracts.ts`, an inline interface in `authorizer-permission.resolver.ts`) were judged not worth a codegen step; revisit if more gRPC services get added or the contracts start changing often.
- **`RpcPermissionGuard` (`libs/auth/src/lib/rpc-permission.guard.ts`) is registered globally per-app** (`app.useGlobalGuards(...)` in each of `invoice`/`product`/`user-access`'s `main.ts`), and `ExecutionContext.getType()` reports `'rpc'` for every microservice transport in Nest, TCP and gRPC alike — `@GrpcMethod` is implemented internally as `@MessagePattern(metadata, Transport.GRPC)`, the same mechanism as a TCP handler. A gRPC handler that's meant to be reachable without a TCP-style `RpcEnvelope` (like `user-access`'s `RoleGrpcController.findAllRoles`, called by `authorizer` on its own behalf, not on behalf of a forwarded end user) must opt out explicitly with `@Public()` — the same `IS_PUBLIC_KEY` decorator `JwtAuthGuard` already uses for HTTP, now also honored by `RpcPermissionGuard`. This was a real bug caught during live verification, not a hypothetical: the first end-to-end request through the new gRPC path failed with `16 UNAUTHENTICATED` from `user-access` because the guard's TCP-envelope check ran against the gRPC call unmodified. Full root-cause writeup: `docs/grpc-authorizer-to-user-access-communication.md`.
- `bff`'s `AuthorizerPermissionResolver` (`apps/bff/src/app/modules/auth/authorizer-permission.resolver.ts`) implements the same `PermissionResolver` interface the old TCP-based `UserPermissionResolver` did (see below) — swapping the transport needed zero changes to `PermissionGuard`, `@RequirePermission`, or any controller.

### PDF generation, S3 storage, and Stripe payments (`invoice` → `pdf-generator`/`media`/`payment`)

`invoice` became an RPC _client_ for the first time here (previously every service besides `bff`
was only ever a callee) — `invoice.service.ts`'s `generatePdf()` calls `pdf-generator` then
`media` over TCP, via new `PdfGeneratorClientService`/`MediaClientService` (`clients/`, same
`BaseTcpClient` shape every `bff` client service already uses), and stores the resulting URL on
the invoice document. This is also why `RpcLoggingInterceptor` now wraps every RPC handler in
`runWithCorrelationContext`: without it, `invoice`'s _outgoing_ calls would carry no correlation
ID/identity (only `bff`, via `CorrelationIdMiddleware`, had ever established that context before),
and the callee's `RpcPermissionGuard` would reject them as unauthenticated — the same bug class
the gRPC series' guard fix caught, just surfacing on the TCP side instead.

- **`StorageProvider` (`apps/media`) and `PaymentProvider` (`apps/payment`) are both the same DI
  shape as `PermissionResolver`**: one small interface, one concrete class bound to it, swappable
  by changing a single `useClass` binding. `media`'s upload handler and `payment`'s checkout-session
  handler both reuse `invoice:write` rather than inventing `media:write`/`payment:write` — both are
  only ever called today as one step inside an invoice-scoped operation, so gating on the
  surrounding business permission is deliberate defense-in-depth, not an oversight.
- **The Stripe webhook is received by `bff`, not by `payment` directly** — see the `apps/payment`
  bullet above for the full reasoning (bff stays the only public ingress; the webhook secret never
  leaves `payment`). A prior plan doc had recorded the opposite decision (`payment` exposing its
  own public endpoint) before this was built; this is the decision that actually shipped.
- **Every third-party Docker image choice in this area was confirmed live, not assumed** — twice
  in a row, a seemingly-standard open-source image turned out to require a paid registry login as
  of a recent licensing change (MinIO: 401 on an anonymous pull from either Docker Hub or quay.io;
  LocalStack: pulls fine, refuses to boot without a paid `LOCALSTACK_AUTH_TOKEN`). `adobe/s3mock`
  is what actually landed in `docker-compose.dev.yml`'s `s3mock` service. The lesson generalized
  directly into how the Kafka image choice above was handled — pulled and smoke-tested first,
  before it went into any plan as settled.
- **Production images only install Chromium for `pdf-generator`** — the Dockerfile's `development`
  stage install is conditional on an `APP_NAME` build arg (now passed by every
  `docker-compose.dev.yml` service, not just this one) for the identical reason: confirmed live
  that the unconditional version inflated every other service's dev image from ~1.1GB to 2.2GB.
- See `docs/pdf-media-payments-implementation-plan.md` for the original plan this was built
  against (local-only, gitignored — see the `docs/` section below).

### Kafka event pipeline (`invoice` → `services/mail`)

The first fire-and-forget hop in this repo — every other cross-service call (TCP, gRPC) is
synchronous request/response. See `docs/message-queues-in-microservices.md` through
`docs/sending-email-smtp-vs-ses.md` (a six-part series) for the full walkthrough. The short version:

- `invoice` is the **producer**, through its transactional outbox (see the `apps/invoice` bullet): `InvoiceEventsProducerService` (`clients/invoice-events-producer.service.ts`) only _writes_ events to the `outbox` collection, inside the transaction of the change they describe; `OutboxRelay` is the only thing in invoice that talks to Kafka. One topic, `invoice.events` (`libs/transports/src/lib/invoice-events.types.ts`), keyed by `invoiceId` so one invoice's events stay ordered; three types, discriminated by `type`: `invoice.demo` (on create, proving the pipe), `invoice.sent` (only from `send()`; carries `pdfKey`, an S3 key — never a URL, since a presigned URL could expire before a lagging consumer reads it) and `invoice.cancelled` (consumed by payment). Every event carries `eventId`. `invoice.sent` replaced `invoice.pdf.generated` (Phase 1), and pre-Phase-2 `invoice.sent` messages carry a public `pdfUrl` and no `eventId`; the Go consumer still handles both (consumer-only fixtures `invoice.pdf.generated.legacy.json`, `invoice.sent.pdf-url.legacy.json`) — delete them with their fallbacks once topic retention has passed. The old fire-and-forget `BaseKafkaProducer`/`createKafkaClientConfig` were removed (a fire-and-forget producer silently drops events when Kafka is down); NestJS consumers use `createKafkaConsumerConfig(clientId, groupId)` (`kafka.config.ts`). **Nest 11's `ServerKafka` awaits the handler and kafkajs only commits after `eachMessage` resolves, so a thrown error is redelivered, not skipped — handlers must be idempotent.** Nest routes Kafka by _topic_: one `@EventPattern(topic)` sees every event type and dispatches on `data.type`.
- **`services/mail` is the consumer — written in Go, not NestJS**, and deliberately lives outside `apps/` (top-level, sibling to `apps/`/`libs/`) since it has its own `go.mod`/`Dockerfile` and nothing for Nx's project graph to attach to. It can't import `libs/transports`, so `services/mail/internal/events/invoice.go` hand-mirrors the TS envelope/event-union shape as a plain JSON contract kept in sync by hand. Uses `segmentio/kafka-go` (pure Go, no cgo) specifically so the final image can be a statically-linked binary on `scratch` — confirmed at **21.9MB**, vs. ~550MB for this repo's production NestJS images. **Delivery semantics (Phase 2):** it used `ReadMessage` with a consumer group, which commits _before_ the handler runs — one SMTP hiccup lost the email for good. Now `FetchMessage` → handle → `CommitMessages`: transient errors retry in place with capped backoff (1 s → 60 s; blocks the partition on purpose — ordered, an outage delays mail instead of losing it); errors wrapped in `failure.Permanent` go to `invoice.events.dlq` (original key/value, error + origin in `x-*` headers) and are then committed; shutdown mid-retry leaves the offset uncommitted. Permanent means _specific to this message_: an undecodable message, a missing S3 object, an SMTP 5xx other than the auth codes (530/534/535/538), SES `MessageRejected`/`BadRequest`. Account-wide failures (bad credentials, unverified domain, throttling) stay transient, so delivery pauses rather than dead-lettering everything. **Don't classify SMTP errors with go-mail's `SendError.IsTemp()`**: it only checks whether the text starts with `4`, so a connection dropped mid-transaction (`EOF`, code 0) would count as permanent; use `ErrorCode()` (0 = not an SMTP reply). Dedupe: `mail:sent:<eventId>` in Redis, checked before sending (an error retries rather than risk a duplicate), marked after (a failed mark is only logged — retrying would resend). Prod Redis is shared with the cache and runs `allkeys-lru`, so dedupe is best-effort under memory pressure (a possible duplicate, never a lost email). It reads PDFs from the private bucket with its own credentials (IAM role in prod). `SMTP_TLS_POLICY` = `mandatory` (default) | `opportunistic` | `none` (plaintext without auth, for a local sink such as Mailpit; refused when `APP_ENV=production`). The image is 35 MB (was 21.9 MB) with the S3 and Redis clients.
- **Dev mail goes to Mailpit** (`mailpit` service, `axllent/mailpit:v1.31.6`; inbox at `http://127.0.0.1:8025`) with `SMTP_TLS_POLICY=none` — no secrets needed. mail-service's SMTP settings are `environment:` entries interpolated from the **shell or the root `.env`**, which override `env_file` — SMTP values in `.env.dev` (where the example file used to tell you to put Gmail credentials) never reached the container, so dev mail could only ever fail its config check. For real Gmail, set `SMTP_*` and `SMTP_TLS_POLICY=mandatory` in the root `.env`. **mail-service is a built image, not bind-mounted:** after any change under `services/mail`, `docker compose -f docker-compose.dev.yml up -d --build mail-service` (dev ran an image from before Phase 2 until this was noticed).
- **Email sending is a DI boundary** (`services/mail/internal/mail`'s `Sender` interface) exactly like `StorageProvider`/`PaymentProvider` on the TypeScript side: `SMTPSender` (Gmail, the `development` default) and `SESSender` (AWS SES, the default everywhere else), both building the same raw RFC 5322 MIME message (SES's attachment support requires its `Raw` content type either way, so there's no simpler path for it to take). `MAIL_PROVIDER` overrides the environment-based default explicitly when set. SES uses the AWS SDK's own default credential chain, same IAM-role-friendly posture as `media`'s S3 client — no static keys in prod.
- **Topics are provisioned, never auto-created.** `infra/kafka/topics.conf` lists every topic (name + partitions); the one-shot `kafka-init` compose service (`infra/kafka/create-topics.sh`) creates missing ones and exits, and invoice/payment/mail-service wait for it (`service_completed_successfully`). The broker runs with `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`. Before this, topics appeared only when a client first asked for one, and the first consumer on a fresh broker lost that race — payment failed to start with `This server does not host this topic-partition` (reproduced: the failed subscribe's own metadata request is what triggered the creation). The script never alters an existing topic (more partitions re-shuffles keys and breaks per-invoice ordering in flight); a mismatch is printed. `libs/transports`' `kafka-topics.spec.ts` fails if the code or a compose `KAFKA_TOPIC_*` variable names an unlisted topic. Prod: `TOPIC_REPLICATION_FACTOR` (1 for the single broker).
- **`KAFKA_LOG_DIRS=/var/lib/kafka/data` is required** in both compose files. Without it the image's env-based config writes to `/tmp/kafka-logs` inside the container while the mounted volume stays empty, so every container recreate silently dropped all topics, unconsumed events and consumer-group offsets (verified: topic id and groups now survive `--force-recreate`). Deploying this onto an existing broker starts from an empty log dir once — drain consumer lag first.
- **`apache/kafka` (official, KRaft mode, single broker) needs its full config supplied together, not incrementally** — touching any one `KAFKA_*` env var switches its entrypoint from "zero-config defaults" to "every KRaft property required," confirmed live by a boot failure from overriding just the advertised listener alone. `KAFKA_ADVERTISED_LISTENERS` has to be the compose service name (`kafka:9092`), not the image's own `localhost` default, or every other container that connects once gets redirected back to its own `localhost` on every subsequent request. `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1` (and the transaction-log equivalents) are required on a single-broker cluster — Kafka's own default of 3 can never be satisfied, and the failure surfaces to every consumer as an opaque "Group Coordinator Not Available" error rather than anything that names the real cause.

### Saga orchestration (`@libs/saga`)

Mongo, Postgres, Stripe, Keycloak, and S3 share no transaction coordinator, so any operation writing to more than one of them in sequence can fail halfway with the earlier writes already committed. `@libs/saga` handles this: `new Saga<TContext>(name).addStep({ name, execute, compensate? })...execute(ctx)` runs steps in order; on failure, it runs each **completed** step's `compensate` in reverse order and throws `SagaExecutionError` (`failedStep`, original `cause`, plus any `compensationFailures` — a failing compensation is logged and collected, never allowed to stop the rest). See `docs/distributed-transactions.md` through `docs/saga-library-and-compensation.md` (a four-part series). The short version:

- **Attach a compensation to the step that made the change, not to whichever later step's failure triggers cleanup.** A failed step never completed, so its own `compensate` never runs. This was a real bug in the first version of `UserService.create()`'s saga (Keycloak-user deletion was on the role-assignment step), caught by that service's existing test suite. The last step usually needs no `compensate` at all.
- **Callers unwrap `SagaExecutionError.cause`** so the original exception type still reaches HTTP/RPC callers (e.g. `ConflictException` for a duplicate email in `user-access`, a 503 back to `bff` from `payment`'s webhook so Stripe retries).
- **Three call sites today:** `user-access`'s `UserService.create()` (refactor of previously hand-rolled compensation); `payment`'s `createCheckoutSession()` (new: expires the Stripe session via `PaymentProvider.expireCheckoutSession()` if the local write fails — previously a still-payable orphaned session); `payment`'s webhook mark-paid (new: if telling `invoice` fails after the local row is marked paid, the row becomes `'reconciliation_required'` — neither reverted to `pending`, which would erase that Stripe has the money, nor left `paid`, which would claim `invoice` agrees).
- **Read generated migrations before trusting them.** Widening `payments.status` to `varchar(32)` for `reconciliation_required` came out of `payment:migration:generate` as `DROP COLUMN` + `ADD COLUMN`, which would have reset every payment's status (paid ones included) to `pending`; rewritten as `ALTER COLUMN ... TYPE` and verified against a real `paid` row.

### Observability (health, logs, metrics, traces)

See `docs/observability-fundamentals.md` through `docs/tcp-trace-context-propagation.md` (a six-part series) plus `docs/observability-implementation-plan.md` (decisions + verification record). The short version:

- **Health (`@libs/health`, always on, no overlay needed):** every service exposes `GET /api/health/live` (heap/RSS; `pdf-generator` also Chromium — drives restarts), `/ready` (its _own_ DB/Redis/S3 — drives traffic), `/dependencies` (peers over TCP/gRPC — diagnostic only, never wired into live/ready, so a peer outage can't cascade). Each app's `src/app/health/` extends `BaseHealthController` and overrides `readinessChecks()`/`dependencyChecks()`. Every gRPC server also serves `grpc.health.v1` (`health.proto`, loaded by `createGrpcServerConfig()`) via `GrpcHealthController`, which must stay `@Public()` — `RpcPermissionGuard` runs on gRPC too. `RedisHealthIndicator` checks `status === 'ready'` before pinging, with a timeout: ioredis's offline queue makes a ping against a down Redis hang forever otherwise. bff's health controller uses `HealthCheckExceptionFilter` so a 503 keeps terminus's body (which check failed) instead of the global problem+json. Compose healthchecks hit `/health/live`; **Docker never restarts an unhealthy container by itself**, so dev runs an `autoheal` sidecar for containers labeled `autoheal=true` (needs the Docker socket, dev only — production's orchestrator liveness probe does this).
- **`CacheModule.forRoot(prefix)` memoizes per prefix.** Nest 11 identifies dynamic modules by object reference, so returning a fresh object per call gave every importing module its own module instance and its own Redis connection (bff had 7).
- **Logs:** apps only write pino JSON to stdout; Grafana Alloy (Promtail's successor — Promtail is EOL) reads container logs through the Docker socket and pushes to Loki. Nothing in an app depends on Loki. `LOG_PRETTY=true|false` overrides the pretty-vs-JSON default (pretty unless `NODE_ENV=production`); the overlay sets `false`. JSON levels are strings (`"level":"error"`). `level` and `service` are Loki labels; `trace_id`/`span_id` are **structured metadata, never labels** (one value per request would explode the index).
- **Metrics + traces (`@libs/telemetry`, off unless `OTEL_*` env enables it — the overlay does):** one OpenTelemetry `NodeSDK` per process, started by each app's `src/instrumentation.ts`, which **must stay the first import in `main.ts`** (instrumentation hooks `require()`; ES imports are hoisted, so starting it from `main.ts`'s body is too late), and `@libs/telemetry` itself must never import `@nestjs/*`. `shutdownTelemetry()` runs in each app's `gracefullyDrain` before `process.exit`. Traces go OTLP/HTTP to Tempo; metrics are served by a Prometheus exporter on internal port **9464** (not the app port). `resolveTelemetrySettings()` decides from env itself and always hands NodeSDK explicit (possibly empty) exporter lists, because NodeSDK's own defaults treat an _unset_ `OTEL_METRICS_EXPORTER`/`OTEL_LOGS_EXPORTER` as "push OTLP to localhost". It defaults `OTEL_SEMCONV_STABILITY_OPT_IN=http` so HTTP metrics use the stable names the dashboards query. Disabled instrumentations: `fs`/`dns`/`net` (noise), and `router` (Express 5 routes through the `router` package, whose instrumentation duplicates the express spans and can't skip middleware). **This exporter emits no unit suffixes** (`http_server_request_duration_bucket`, not `..._seconds_...`) — write PromQL against what `/api/v1/label/__name__/values` actually returns.
- **TCP trace propagation is manual** (`@libs/telemetry/rpc-tracing`, imported by subpath — it depends on `@opentelemetry/api` only): Nest's TCP transport has no headers, so `RpcMeta` carries W3C `traceparent`/`tracestate`, filled by `createRpcEnvelope()` from the active context. `BaseTcpClient.send()` starts a CLIENT span and builds the envelope inside it; `RpcTracingInterceptor` (`@libs/interceptors`) continues it as a SERVER span and must be registered **first** in `useGlobalInterceptors(...)` (outermost, so RPC log lines carry its `trace_id`) — it subscribes to the handler inside the span's context, not just calls `next.handle()` there. It ignores messages with no `traceparent` (gRPC is traced by its own instrumentation). Both sides record `rpc.client/server.duration` (ms; labels: system/service/method/`error_type` — never ids). A 4xx-style RPC outcome is recorded but not marked as a span error. The active OTel trace id is the `traceId` everywhere: `x-trace-id` header, `RpcMeta.traceId`, pino `trace_id`, and bff's problem+json `traceId` (which, since tracing, is distinct from its `correlationId` field).
- **Specs that need real OTel** (propagation, active-context assertions) use `installOtelTestHarness()` from `@libs/telemetry/otel-test-harness` — in-memory exporter, real W3C propagator and async context manager. Spec-only; never import it from app code.
- **Stack config** lives in `infra/observability/` (Loki, Alloy, Tempo, Prometheus, Grafana provisioning + dashboards `logs.json`/`services.json`, read-only in the UI — edit the JSON). Image versions are pinned. **Tempo is 3.0**: 2.x's `compactor:` block no longer exists (retention is `backend_scheduler`/`backend_worker`); monolithic mode needs no Kafka. Tempo's exemplars are labeled `traceID`, not `trace_id`. Loki and Tempo images are distroless (no shell) — no compose healthcheck is possible for them.
- **Circuit breaker failure rule:** `CircuitBreaker` counts only 5xx, 429, and non-HTTP errors, classified **by status**, and resets on success (the threshold is consecutive failures). It used `instanceof NotFoundException` etc., which never matched `BaseTcpClient`'s plain `HttpException(body, 404)` — five lookups of a missing invoice opened the breaker for every invoice endpoint.

### Shared libs (`libs/*`)

- `@libs/configuration` — process-wide config singletons (not NestJS `ConfigService` DI in most places; each app's `src/configuration/index.ts` calls `loadEnvironmentFiles()` then constructs and validates a `Configuration` instance eagerly at module load time, exported as `CONFIGURATION`). Several app-level providers read this singleton directly rather than injecting a config token — see the note on `MongoDbModule` below for why that matters.
- `@libs/schemas` — the only place Mongoose `@Schema()` classes live (`Invoice`, `InvoiceItem`, `ClientSnapshot`, `AuditLog`), used by `apps/invoice`. `BaseSchema`/`BASE_SCHEMA_OPTIONS` set `versionKey: 'version'` and `optimisticConcurrency: true` (required for Mongoose to bump `version` on a plain `.set()+.save()`, not just on array mutations — needed for the If-Match optimistic-concurrency flow). The `Invoice` schema's `pre('validate')` hook is what (re)computes `subtotal`/`vatTotal`/`total` server-side; it always runs, so the client-submitted totals in a request body are ignored. `apps/product`'s TypeORM entities are app-local instead (`apps/product/src/database/entities/`), not in a shared lib — each app that owns a database wires its own entities/connection (see the note on `MongoDbModule`/`PostgresModule` below).
- `@libs/transports` — RPC plumbing described above, plus `TCP_PATTERNS`, `ServiceName`, `TCP_CLIENT_TOKENS`, `createTcpServerConfig`/`createTcpClientConfig` for the TCP side, and `GrpcServiceName`, `GRPC_SERVICES`, `GRPC_CLIENT_TOKENS`, `createGrpcServerConfig`/`createGrpcClientConfig`, plus the `.proto` files themselves (`src/proto/`), for the gRPC side — see the gRPC section above.
- `@libs/cache`, `@libs/circuit-breaker`, `@libs/rate-limit` — each is a `forRoot()`/`forRootAsync`-style Nest module wrapping the respective concern; only the BFF uses rate-limit and circuit-breaker, both `bff` and `invoice` use cache.
- `@libs/saga` — saga orchestration for operations that write to more than one system with no shared transaction (see the Saga section above). Deliberately **not** a Nest module: a plain `new Saga<TContext>(name)` per call, since unlike a circuit breaker it has no state to share across calls.
- `@libs/audit-log` — `AuditLogModule` (global) + `AuditLogService.record()`, backed by its own Mongo collection via `@InjectModel`. Import it directly with `MongooseModule.forFeature([...])` for the model it needs rather than assuming another module's global registration will provide it — see the gotcha below.
- `@libs/logging`, `@libs/middlewares`, `@libs/interceptors`, `@libs/filters`, `@libs/decorators` — pino-based structured logging (`LoggingModule.forRoot({ serviceName })`), correlation-id propagation, response envelope/timeout/RPC interceptors (incl. `RpcTracingInterceptor`), the global exception filter.
- `@libs/health` — `BaseHealthController`, `RedisHealthIndicator`, `tcpPeerCheck`/`grpcPeerCheck`, `GrpcHealthController`, `HealthCheckExceptionFilter`, `withTimeout` (see the Observability section).
- `@libs/telemetry` — `startTelemetry`/`shutdownTelemetry` (barrel; SDK-heavy, only for `instrumentation.ts`/`main.ts`) and `rpc-tracing` (subpath; API-only, safe from any lib) — see the Observability section.
- `@libs/interfaces` (imported as `@libs/interfaces/gateway`) and `@libs/shared/types` — request/response DTOs and shared domain types/enums/pagination helpers used by both `apps/bff` and `apps/invoice` so the two sides of the RPC boundary can't drift.

### Per-app database wiring (`apps/invoice/src/database/`, `apps/product/src/database/`, `apps/user-access/src/database/`)

Each app that owns a database wires its own database module (not shared — `invoice`'s `MongoDbModule` is app-local because it can have different read-replica needs, see `MongoDbModule.withReadReplicas()`; `product` and `user-access`'s `PostgresModule`s follow the same shape for symmetry, even though they currently point at the same physical Postgres instance). A dynamic module's `imports` (e.g. `MongooseModule.forRootAsync({ inject: [...] })` / `TypeOrmModule.forRootAsync({ useFactory: ... })`) can only resolve providers declared in that _same_ module's own `providers` array or in modules _it_ imports — never a provider declared only by whatever module imports it. Read the app's own `CONFIGURATION` singleton directly in these low-level provider factories instead of injecting an app-level DI token for it. Each feature module that uses an entity/model registers it explicitly too (e.g. `TypeOrmModule.forFeature([...])` inside `ProductModule`, not only in the global `PostgresModule`) rather than relying on a `@Global()` module's registration reaching everywhere implicitly — that assumption is exactly what masked the real `AuditLogService` bug (a wrong injection token) behind what looked like a module-visibility problem.

### Nx per-app project parity

`apps/invoice/project.json` is the reference shape for a deployable app: `build`, `serve`, `type-check` (+ `integration` when it has integration tests). The production `Dockerfile` runs `nx run ${APP_NAME}:build:production` and ships `dist/apps/${APP_NAME}/` as is. None of the apps have a per-app `package.json` (they rely on the root `package.json` + webpack's `generatePackageJson: true`, which writes the pruned `package.json` + `pnpm-lock.yaml` the runtime stage installs from) — don't add one when scaffolding a new app, and keep `generatePackageJson: true` and any runtime-loaded files in its webpack `assets`. A Postgres-backed app additionally needs a `seed-*`-style custom target if it has seed data — see `apps/user-access/project.json`'s `seed-roles` target (an `nx:run-commands` executor invoking a ts-node script) for the pattern.

### Authentication & authorization (Keycloak)

`bff` is the only service that talks to Keycloak directly — `invoice`, `product`, and `user-access` never see a raw Keycloak token or call its JWKS endpoint themselves; they trust the identity `bff` attaches to the `RpcEnvelope`, the same way they already trust `correlationId`/`traceId`.

- **Local Keycloak**: a `keycloak` service in `docker-compose.dev.yml` (dev only, not in prod) auto-imports `infra/keycloak/realm-export/einvoice-realm.json` on boot — realm `einvoice`, client `einvoice-bff` (confidential, direct-access-grants enabled, with an audience protocol mapper so `aud` includes the client id), realm roles, and three dev-only test users (`dev.admin`/`dev.accountant`, plus `dev.platform` with the `platform-admin` realm role; password `DevPassw0rd!` — same non-secret-boundary caveat as the other dev fixture credentials in this repo). Since Phase 3 the organization roles (`admin`/`manager`/`accountant`/`viewer`) come from **memberships**, not realm roles — a freshly imported realm's users have none until `nx run user-access:seed-dev-memberships` (dev only, idempotent) makes `dev.admin`/`dev.accountant` members of the default organization. Only `platform-admin` is still read from the realm. Editing that JSON requires a volume reset to re-import (`docker compose down keycloak -v`) — Keycloak's `IGNORE_EXISTING` import strategy skips a realm that already exists.
- **`@libs/auth`** — the shared lib: `KeycloakConfiguration`, a passport `JwtStrategy` verifying signatures against Keycloak's JWKS (via `jwks-rsa`'s `passportJwtSecret`, cached, with issuer/algorithm checks), `JwtAuthGuard` (respects `@Public()` to bypass), `PermissionGuard` + `@RequirePermission(...)`, `@CurrentUser()`, `RpcPermissionGuard`. `PermissionGuard` is deliberately **not** provided by the lib's own `KeycloakAuthModule.forRoot()` — it needs a `PERMISSION_RESOLVER` implementation that can only be assembled by an app that also has `UserService` (or equivalent) in scope, so the consuming app re-declares `PermissionGuard` as a provider in its own module alongside its own `PERMISSION_RESOLVER`. This is the same dynamic-module provider-resolution rule documented above for `PostgresModule`/`MongoDbModule` — a provider is only resolvable from its own module's `providers` or the modules it imports, never from whatever imports it. `invoice`/`product`/`user-access` import `RpcPermissionGuard` and `RequirePermission` via their direct subpaths (`@libs/auth/rpc-permission.guard`, `@libs/auth/require-permission.decorator`), not the lib's barrel `@libs/auth` — importing the barrel would pull in `KeycloakAuthModule`'s Passport/JWKS machinery (and the ESM packages that come with it) into services that never talk to Keycloak at all.
- **`apps/bff/src/app/modules/auth`** — `POST /auth/login` (`@Public()`, Resource Owner Password grant against Keycloak — the default flow, since `bff` is a pure JSON API gateway with no server-rendered login page) and `AuthorizerPermissionResolver` (implements `PermissionResolver` as a gRPC client to `apps/authorizer`, which resolves role names to permissions and caches that lookup itself — see the gRPC section above; this replaced the original TCP-based `UserPermissionResolver`, deleted, with zero changes needed to `PermissionGuard` or anything downstream of the interface). Also `GET /auth/login/redirect` + `GET /auth/callback` — the Authorization Code flow, which exists _only_ because a federated identity provider (Google) has no equivalent of handing over a password directly; it has to go through a real browser redirect. `KeycloakConfiguration.PUBLIC_BASE_URL` is deliberately separate from `BASE_URL` — the browser following the redirect can't resolve Keycloak's internal Docker hostname the way `bff` itself can for server-to-server calls (token exchange, JWKS). Login `state` (CSRF protection, one-time use) lives in Redis via `CACHE_MANAGER`, not a signed cookie — `bff` has no cookie/session infrastructure. The redirect handler needs `@SkipResponseWrap()` (`@libs/interceptors`) alongside `@Redirect()` — without it, the global `ResponseInterceptor` wraps the `{ url, statusCode }` object `@Redirect()` needs into the standard API envelope _before_ Nest's own redirect handling ever sees it, so the response silently falls through to a normal 200 instead of a 302. Also `POST /auth/refresh` and `POST /auth/logout` (both `@Public()` — the refresh token itself is the credential, not a still-valid access token). Refresh token **rotation** is not a Keycloak default — a fresh realm leaves a refresh token reusable until its own expiry, confirmed live before the realm config explicitly set `revokeRefreshToken: true` + `refreshTokenMaxReuse: 0`; without that, a leaked refresh token stays useful to an attacker for its entire lifetime, and the code comment claiming "Keycloak rotates by default" would have been actively wrong. `logout()` ends the Keycloak session a refresh token belongs to (stopping further refreshes) but never revokes an already-issued access token from that session — same limitation as `KeycloakAdminService.setEnabled()`, since JWT verification never re-checks Keycloak per request.
- **Identity propagation**: `JwtAuthGuard.handleRequest()` calls `setIdentityOnCurrentContext()` (`@libs/logging`) to mutate the request's existing correlation `AsyncLocalStorage` store in place — `RpcMeta` (`@libs/transports`) now carries `userId`/`roles`/`permissions` alongside `correlationId`/`traceId` on every outgoing RPC call, automatically, with no per-call-site wiring needed. `PermissionGuard` resolves permissions (via `PERMISSION_RESOLVER`) for **every** authenticated request now, not only ones `@RequirePermission` gates — enforcement stays conditional on the decorator, but propagation doesn't, so downstream services always receive a caller's real permissions to check themselves.
- **Downstream enforcement** (`invoice`/`product`/`user-access`): each service registers `RpcPermissionGuard` globally in its own `main.ts` (`app.useGlobalGuards(app.get(RpcPermissionGuard))`, with `RpcPermissionGuard` added to that app's own `AppModule.providers`). It reads `meta.userId`/`meta.permissions` straight off the incoming `RpcEnvelope` — no Keycloak call, no `PERMISSION_RESOLVER`, just a comparison against whatever `@RequirePermission(...)` the handler declares (mirroring `bff`'s exact permission strings). A call with no valid envelope at all is rejected outright (401), independent of whether that handler declares a permission — these RPC ports should only ever be called by `bff`. One deliberate exception: `role-rpc.controller.ts`'s `ROLE.FIND_ALL` handler has **no** `@RequirePermission` — `bff`'s own `PermissionGuard` calls this exact pattern to resolve _which_ permissions a caller has in the first place, so gating it on a permission would make that resolution call require a permission it can't possibly have yet. Because guards run before interceptors in Nest's pipeline, `RpcPermissionGuard` throws a pre-shaped `RpcException` directly (`{ code, status, error, message }`) rather than a plain `HttpException` — an exception thrown from a guard never reaches `RpcExceptionInterceptor`'s `catchError`, so a plain exception would surface at `bff` as an opaque 502 instead of the correct 401/403. This guard verifies the _shape_ of what `bff` already resolved, not the claim cryptographically — a party with raw TCP access to one of these ports (published to the host in dev, not in prod) could forge a well-formed envelope claiming any permission. The real boundary in production is `docker-compose.prod.yml` exposing these ports only on the internal network.
- **`isRpcEnvelope()` and `undefined` payloads**: `createRpcEnvelope(undefined, ...)` (used by any RPC call with no payload, e.g. `ROLE.FIND_ALL`) produces `{ data: undefined, meta: {...} }` — but `JSON.stringify` drops object keys whose value is `undefined`, so the envelope arrives over the wire with no `data` key at all. `isRpcEnvelope()` validates envelope-ness by the `meta` shape alone for exactly this reason; checking for a literal `'data' in candidate` key (as it briefly did) silently misses every no-payload call, discarding `meta` — and therefore identity — along with it.
- **JWKS resilience**: `JwtStrategy` doesn't use `jwks-rsa`'s `passportJwtSecret()` convenience wrapper directly — it goes through `JwksCacheService`, which wraps a `JwksClient` with a Redis-backed fallback (`bff::keycloak:jwks:key:<kid>`, 1h TTL). `jwks-rsa`'s own in-memory cache only helps once a key has already been fetched in that process; a freshly started `bff` instance with nothing in memory yet would otherwise reject every token during a Keycloak outage. On a live JWKS fetch failure, it falls back to the last known-good key from Redis if one exists, logging a warning — verified by stopping Keycloak, restarting `bff` (cold cache), and confirming a previously issued token still verifies.
- **`user-access`'s `KeycloakAdminService`** (`@libs/auth/keycloak-admin.service`, imported by subpath, not the barrel — same reasoning as `RpcPermissionGuard`): authenticates as `einvoice-admin-cli`, a separate client-credentials-only client from `einvoice-bff`, whose service account needs `manage-users` **and** `view-users` **and** `view-realm` on the `realm-management` client (fetching a role by name for role-mapping calls needs `view-realm` specifically — `manage-users`/`view-users` alone 403s on it, caught only by actually calling the API, not by reading Keycloak's docs). `UserService.create()` provisions Keycloak-first-then-Postgres (nothing to clean up if Keycloak fails; the Keycloak user gets rolled back via `deleteUser()` if the later Postgres write fails). Since Phase 3, roles are no longer synced to Keycloak realm roles — a user's role is their membership's, per organization. `deactivate()` ends the membership in the caller's organization and best-effort disables the Keycloak account only when no active membership is left anywhere (logged, not thrown, on failure) — this stops _new_ tokens being issued, not already-issued ones, since JWT verification never re-checks Keycloak per request; real-time revocation of live tokens is a separate, unbuilt piece. Does **not** set a password on created users (see the service's own doc comment) — this project's `UserEntity` deliberately has no password field, and there's no invite/email flow yet to hand a generated one to anyone, so a Keycloak account created this way needs its password set separately before it can log in.
- **`docker compose restart` vs `up -d`**: a real trap hit while wiring the above — `restart <service>` restarts the _existing_ container with whatever environment it was originally created with; it does **not** re-read `docker-compose.dev.yml`. New or changed environment variables (like the `KEYCLOAK_ADMIN_CLIENT_*` vars this needed) silently don't take effect until the container is recreated: `docker compose up -d --no-deps <service>`. Restarting alone is fine for code changes (bind-mounted, re-read on process start) — only compose-file changes need recreation.
- **Global guard order in `apps/bff/src/main.ts`**: rate limit → `JwtAuthGuard` → `PermissionGuard`. A route needs `@Public()` to skip authentication entirely (health check, `/auth/login`); a route with no `@RequirePermission(...)` is authenticated but not permission-checked (any valid token passes).
- **Jest + ESM-only packages**: `@nestjs/passport`, `@nestjs/axios`, `jwks-rsa`, and `jwks-rsa`'s own `jose` dependency all ship `"type": "module"`. Jest's default `node_modules` exclusion leaves their `export`/`import` syntax untransformed, breaking any spec that transitively imports `@libs/auth`. `apps/bff/jest.config.cts` fixes this with a pnpm-aware `transformIgnorePatterns` — the pattern has to match inside `node_modules/.pnpm/<pkg>@<version>/node_modules/<pkg>`, not the top-level symlink, since pnpm's virtual store nests the real files there. Adding another ESM-only dependency anywhere that reaches `@libs/auth` (or any other lib) means extending that regex, not writing a parallel one.
